# Lab 09: 最終設計レビュー（ECS vs EKS）

## 学習目標

- 同じ要件に対して ECS 構成案と EKS 構成案を描き、比較軸ごとに違いを説明できる。
- 「EKS を使うこと」を前提にせず、要件と条件から採用・不採用を判断し、反対案と判断が変わる条件を示せる。
- 定量比較（費用など）の条件を揃え、確認できた事実と推測、不確実性を区別して記録できる。
- Phase 1〜8 で自分が観察したことを、設計判断の根拠として引用できる。

## 前提条件

Phase 1〜8 の学習（またはその範囲の理解）があること。Phase 6〜8 を実際には実行していない場合は、そのことを「実行していない」と明示して記録し、公式資料で補います（実行していない内容を観察したことにしない）。

この Lab はコードを書かず、**クラウドの操作もしません**（AWS API の呼び出し、リソース作成、`terraform apply` は行いません）。費用は AWS 公式の料金ページと AWS Pricing Calculator を自分で見て見積もります。AWS 費用は発生しません。

## 設計課題（実装前に考える）

[ecs-vs-eks.md](ecs-vs-eks.md) の課題シナリオ（仮定であり、あなたの要件ではありません）を前提に、各比較軸の問いに答えます。「どちらが正しいか」ではなく、**どの条件ならどちらを選ぶか**を理由とともに書いてください。

1. 初期構築: どちらが要件実現までの構成要素が少ないか？
2. 運用責任: ノード、パッチ、ネットワーク、アドオンの管理責務はどちらにあるか？
3. スケール: Pod/Task と Node/Capacity の独立性、負荷への追従はどう違うか？
4. 可用性: ノード / AZ / DB 障害にどの設計で対応するか？
5. セキュリティ: IAM、ネットワーク、コンテナ権限、監査で何が必要か？
6. コスト: 常時費用、変動費、運用人件費、移行費用の差は何か？
7. 開発体験: GitOps、共通基盤、エコシステム、組織の学習負荷はどう違うか？
8. 長期戦略: 既存技術、移植性、マルチクラスタ要件が判断に影響するか？

## 実装タスク

1. [構成図の比較](architecture.md) を読み、WorkBoard の各要素が ECS と EKS でそれぞれ何に対応するかを自分の言葉で書き出す。
2. 要件を整理する。[ecs-vs-eks.md](ecs-vs-eks.md) の課題シナリオに、自分が置く仮定（利用者数、可用性の目標、運用人数、将来のサービス数、既存技術など）を明示して足す。
3. 同一要件で ECS 構成案と EKS 構成案を描く。起動タイプ（Fargate / EC2）、ノード運用の有無、ALB、RDS、IAM、ECR、ログの選択を案ごとに決める。
4. 比較表を埋める。各軸で「確認した事実」「根拠（公式資料 / Phase 1〜8 で観察したこと）」「推測」を分ける。
5. 採用判断と反対案、判断が変わる条件を書く。
6. 不確実性と追加調査を書く。確認できなかった点は成功扱いにしない。
7. 結果を **学習ポータルの学習メモ**（項目は「学習メモ」節）に記録する。

## 検証方法・期待結果

このラボは実行して確認するのではなく、**資料を読み、条件を揃えて見積もり、根拠をたどれる形で記録する**ことが検証です。確認はすべて公式資料の閲覧と、Pricing Calculator 上での試算です。調査日と参照した資料の URL を記録してください。

### 1. 構成要素と責任分界を公式資料で確認する

[ADR-0017（提案）](decisions/0017-ecs-vs-eks-evaluation-method.md) の Evidence にある ECS と EKS の公式ドキュメントを読み、チェック観点を決めて確認します。

- 起動タイプ（Fargate / EC2）ごとに、OS・パッチ・容量管理の責任が誰にあるか。
- タスクロール / Pod Identity など、コンテナにどう IAM 権限を渡すか。
- ロードバランサーと ECS サービス / EKS の Service・Ingress の対応。
- ログの出力先と、収集のために自分で用意するもの。

期待結果は、比較表の各行に「どの資料のどの記述か」が付いていることです。

### 2. 費用を同じ条件で見積もる

[ecs-vs-eks.md](ecs-vs-eks.md) の「定量比較で揃える条件」を先に決め、ECS・EKS 両案を同じ条件で [AWS Pricing Calculator](https://calculator.aws/) に入力します。料金は変動するため、この教材の資料に値は載せていません。公式の料金ページ（ECS / Fargate / EKS）も併読し、計算ツールに含まれない費用（運用人件費、移行費用、データ転送など）が何かを書き出します。

期待結果は、条件（region、時間、台数、構成、調査日）が記録され、他の人が同じ条件で再計算できることです。

### 3. Phase 1〜8 の観察を根拠に結びつける

比較表の「Phase 1〜8 で観察したこと」の列に、自分の学習メモのどの記録が根拠になるかを書きます。観察していない軸は空欄にせず「未観察」と書き、追加調査へ回します。

### 4. 反対意見を試す

自分の結論と反対の案を、最も有利な条件で擁護する文章を書いてみます。どの条件が変われば結論が逆転するかを「判断が変わる条件」に残します。

## 完了条件

- [ ] 仮定と要件を明示し、ECS 案と EKS 案を同一要件で描いた。
- [ ] 8 つの比較軸すべてで、事実・根拠・推測を区別して比較表を埋めた。
- [ ] 費用を同じ条件で見積もり、条件と調査日を記録した（料金の値を記憶や古い資料から書いていない）。
- [ ] 採用判断、反対案、判断が変わる条件を説明できる。EKS または ECS のどちらかを無条件の正解として扱っていない。
- [ ] 不確実性と未確認の点を、追加調査の項目として残した。
- [ ] 下記に結果・未実施の項目・設計課題への回答を記録した。
- [ ] 設計課題に答えた**後で** [ADR-0017（提案）](decisions/0017-ecs-vs-eks-evaluation-method.md) を読み、自分の比較の進め方と比べた。納得できたら ADR の Status を「採用」に変更し、異なる判断をした点は理由を学習ポータルの学習メモに残した。

## 学習メモ

観察結果と設計課題への回答は、この README ではなく**学習ポータルに入力します**（各自の PC の Git 管理外 `learning-portal/.data` にだけ保存され、リポジトリには残りません）。実行していない項目は「省略」と理由を書きます。記録する項目は次のとおりです。

- 実施日・調査日
- 置いた仮定と要件
- ECS 案の構成（起動タイプ、主要な構成要素）
- EKS 案の構成（ノード管理方式、主要な構成要素）
- 費用見積もりの条件（region・時間・台数・構成）と使った資料
- 比較軸ごとの比較結果と根拠
- Phase 1〜8 の観察のうち根拠にしたもの
- 採用判断と理由
- 反対案と判断が変わる条件
- 不確実性・未確認の点・追加調査
- 疑問・未解決事項
